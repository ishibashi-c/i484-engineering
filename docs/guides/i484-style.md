# i484-style

i484-styleは、既存の制作機能と基本品質へ個人の好みを重ねるSkillです。工程全体はCompound Engineeringが担当します。共通の好みと3つの内部領域を同じパッケージで管理し、今回に必要な資料だけ読みます。

## 適用条件

新規UIと説明資料は、名前の指定がなくても適用対象です。既存ブランドと明示指定を優先し、修正依頼では対象範囲を維持してください。幾何学イラストは、その表現を指定した場合だけ対象にします。写真・写実や指定のない画像依頼へ、幾何学表現を追加しません。

| 内部領域 | 依頼の例 | 主な契約 |
|---|---|---|
| product-ui | 管理画面の新規設計、既存フォームの変更、UI評価 | 操作、状態、復旧、アクセシビリティと好みの両立 |
| communication | 比較資料の視覚設計、単一HTMLの引き継ぎ書 | 内容と根拠、読み順、図の説明、可搬性 |
| illustration | 街の写真の幾何学化、指定された幾何学図版 | 主題の関係、入力画像の役割、生成仕様、実画像の評価 |

独立HTMLを求めていない資料では、適切な制作機能を使い、HTML変換を必須にしません。会話内の可視化と独立HTMLの制作は用途を区別します。幾何学の視覚文法だけが必要なら、画像を生成せず、構図と色の役割などを制作へ渡せます。

## 基本品質と好み

共通方針の中心は、主題の関係、文字と色の役割、明快な幾何学、密度と静かな領域です。用途に合わせて選び、媒体を横断して同じ色数や形状を強制しません。

UIの操作・状態・復旧に影響する場合は、関連するUX条件を設計前に読みます。純粋な見た目の修正では不要です。外部のUI Skills MCPとChecklist Designは、利用可能で、判断に必要な場合だけ知識や抜け漏れの確認を補います。接続や外部Skillの一括導入を要求せず、外部の工程へ権限を移しません。

画像参照は、編集対象、主題、作風、補助を区別します。街の写真を変換する場合は必要な位置関係を保ち、作風を別の主題へ適用する場合は元画像の固有配置を転用しません。AIによる事前評価は、ユーザーの承認や永続的な好みの更新を意味しません。

## 成果物の確認

表示や操作の主張には、それに対応する実際の観測が必要です。HTMLの構造検査だけを表示確認、画像生成の成功だけを視覚品質の合格とは扱いません。確認できない条件は未確認として報告します。検証の実行方法、レビュー、Git、公開はCEとProjectの指示が決めます。

## モデルと保守

Luna 6を想定し、入口は領域を選ぶための条件に絞りました。必須の成果物契約と読み込み条件は保持し、重複した説明を整理しています。[最新の公式ガイダンス](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)も、モデルによって必要な指示が異なることを指摘しています。構成の整理だけで、Lunaの品質や削減率が向上したとは判断しません。

実行時の条件は[SKILL.md](../../skills/i484-style/SKILL.md)、共通の好みは[共通方針](../../skills/i484-style/references/style-principles.md)、出典は[資料一覧](../../skills/i484-style/references/sources.md)で管理します。環境への導入は[個人用開発環境の導入書](personal-environment.md)を参照してください。

旧i484-product-design、i484-visualize、i484-geometric-illustrationはこの入口へ統合しました。更新時の除去対象に登録し、旧入口と新入口を併用しません。既存成果物や元の出典・帰属は保持します。
